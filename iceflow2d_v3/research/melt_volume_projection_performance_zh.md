# 界面水量校正的并行开销测量（2026-09-22）

**在本机 RTX 5090、450×150 网格上，GPU 修正路径约 0.125 ms/次；当前 NumPy/SciPy 参考路径约 1.51 ms/次。若每 8 个 LBM 步修正一次，按实际测得的基准步耗时估算，总耗时分别增加约 2.5% 和 30%。**

GPU 数字以连通区域掩码已知、单层容量足够为前提。这是独立算子的计时和耦合步耗时推算，不是已经接入守恒修正后的完整仿真加速比，也不是多 GPU 并行效率实测。

## 1. 测量设置

- 硬件：NVIDIA GeForce RTX 5090，32607 MiB，驱动 570.211.01；Taichi 1.7.4、Python 3.13.9、CUDA 后端。
- 基准是当前 450×150、W=5、`consistent_flux` 四冰块算例，包含流动、刚体运动、传热及既有稳定性检查。先推进 18000 步至 0.15 s，再计时 5 组、每组 512 步；无文件输出。
- 基准 LBM 步耗时中位数 **0.629301 ms**，5 组的 P10/P90 为 0.625710/0.632420 ms。这是 0.15–0.171333 s 的局部性能样本，不是整段 5 s 的平均耗时。
- 每种修正工况计时 60 次，预先完成编译和预热；每次计时前后 `ti.sync()`。恢复相同测试状态的开销不计入修正时间。
- 修正对象是规定完全融化的 64 格区域，负向修正量为 5.312 格，即 64 格候选水减到密度比 0.917 要求的 58.688 格。计时不包含材料熔化本身。
- 保存场工况读取此前 W=5 末态的真实 phi，作为静止修正工况的背景；没有用这次计时验证动态流场、收缩瞬态或热量守恒。

## 2. 实测单次开销

| 网格 | 相场工况 | CPU 参考路径 / ms | GPU 路径 / ms | 实际改变 phi 的格点数 |
|---|---|---:|---:|---:|
| 32×48 | 清晰液面水池 | 0.280050 | 0.092828 | 28 |
| 32×48 | 空气中独立融水滴 | 0.276255 | 0.092301 | 64 |
| 450×150 | 清晰液面水池 | 1.186397 | 0.119334 | 444 |
| 450×150 | 保存的 W=5 相场 | 1.510047 | 0.125091 | 63936 |
| 900×300 | W=5 保存场的 2×2 复制放大 | 6.084220 | 0.348895 | 255744 |

CPU 参考路径包含 phi 下载、原来的 NumPy/SciPy 连通区域标记与有界修正、修正场上传，以及真实 h/g 分布函数同步。固定流体/融化掩码和目标值已缓存，未把其初始化分配算入每次事件。

GPU 路径执行：候选水及界面带/容量统计 → 有界更新并统计舍入后的水量 → 单点关闭浮点尾差 → 使用同一个 `_apply_phase` 同步 h/g。相场与中间数据留在设备端，计时内不读取主机端水量标量；连通区域掩码、融化掩码和目标已知。

450×150 保存场工况的 CPU 分段中位数为：

| 环节 | ms |
|---|---:|
| phi 下载 | 0.109391 |
| NumPy/SciPy 连通标记、掩码、求和及修正 | 1.282609 |
| 上传及 h/g 同步、等待完成 | 0.117828 |

各段中位数不必严格相加成总时间中位数。当前 CPU 路径的主要成本是 CPU 上的数组处理，数据往返和同步也增加了开销。

GPU 保存场单次时间的 P10/P90 为 0.123083/0.128570 ms。所有工况的正、负方向水量误差均小于 2.798e-08 格；负向修正后的 [0,1] 有界性、无关水体不变、从 populations 恢复 phi 不撤销修正均通过检查。

## 3. 对完整求解耗时的估算

设每 K 个 LBM 步做一次修正，则：

```text
平均每步增加耗时 ≈ T_correction / K
总耗时增加比例   ≈ T_correction / (K * T_LBM)
```

采用实际 W=5 保存场的修正成本和本次基准步时间：

| 实现 | 单次修正 / ms | 每步修正：总耗时增加 | 每 8 步修正：总耗时增加 |
|---|---:|---:|---:|
| 当前 CPU 参考实现 | 1.510047 | +239.96% | +29.99% |
| GPU 修正路径，连通区域已知 | 0.125091 | +19.88% | +2.48% |

GPU 每 8 步一次时，平均步耗时估算从 0.629301 ms 增至 0.644937 ms，对应求解速度下降约 2.42%。这里的“总耗时增加”和“速度下降”是不同分母，不应混用。

当前热更新间隔为 8 个 LBM 步，因此可考虑在一次热更新结束后汇总执行一次校正。该频率只约束校正时刻的总水量；若要求每个 LBM 步都满足约束，应采用每步修正的成本预算。在每个热子步内重复校正时，次数和成本还要增加。

这些推算没有包含新加入的能量重映射、动态连通区域识别或完整模型耦合验证成本。优化归约和复用已有质量统计可以降低增量；新增同步、多个界面层和拓扑变化也可能提高增量。

## 4. 并行性真正受什么影响

**单元更新容易并行，归约是全局依赖。** 各格点的候选水、容量和 h/g 更新相互独立；但更新系数需要先获得全局水量及容量，不能完全避免阶段间同步。单层算法是 O(N) 的场遍历，没有泊松方程求解。若需要 L 层，当前全场扫描方式约为 O(LN)。

**归约方式很重要。** 本次初版逐格向同一 f64 计数器累加，450×150 保存场耗时约 0.425 ms/次。改为最多 2048 个并行线程通道，各自先累加多个相邻批次的格点，再合并局部结果，单次降至约 0.125 ms。水量精度不变。Taichi 对并行归约提供线程局部存储等优化，但仍需按实际字段和网格验证：[Taichi 性能文档](https://docs.taichi-lang.org/docs/performance)。

**当前“界面带”条件并不总是窄带。** 原型把连通域内 0<phi<1 的格点都列入候选带。当前 W=5 末态中所有 63936 个有效流体节点都落在这个区间，因此本工况实际改变了全部流体节点。清晰液面工况只改变 444 个节点。若要限制为真正的自由液面附近，应明确界面带定义并重新检查容量、有界性和不影响无关水体的条件，不能只凭“只改界面”假定成本很小。

**连通区域是另一项成本。** 当前 CPU 参考每次运行 SciPy 连通标记；GPU 微基准已经给定选中的连通域，未实现任意拓扑变化时的 GPU 连通标记。因此 0.125 ms 不能直接当作任意破碎、多水滴场景的完整修正成本。单一水池或连通关系可缓存时，这条性能路径更接近实际可用方案。

**多 GPU 不能直接照搬 2.5%。** 分区后，各卡可并行计算局部水量与容量，但需要跨卡归约；严格尾差闭合还需要修正后的总量和修正节点选择。小规模标量通信仍有同步延迟，跨分区连通域还需额外处理。AllReduce 的语义见 [NVIDIA NCCL 文档](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/collectives.html)。本次没有测多 GPU 强扩展或 MPI 效率。
